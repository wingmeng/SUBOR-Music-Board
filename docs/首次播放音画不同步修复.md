# 首次播放音画不同步修复

## 缺陷现象

冷启动（刚打开 / 刷新页面）后导入一首简谱并开始播放：点击播放后进度指示器已经开始走动，
但声音还没发出来，**从第一个音就开始不同步**，声音比指示器慢几个格子（数百 ms 量级）。
**只要中途按一次暂停或停止，再次播放就正常。**

## 第一轮修复（未解决）：100ms 预调度偏移对齐

`scheduleAllNotes()` 以 `baseTime = engine.currentTime + 0.1` 作为第一个音符的绝对时间，
而 `play()` / 循环分支的 `playbackWallStart` 未同步 +100ms，导致声音恒定滞后指示器 100ms
（`restartFromCurrentPosition()` 早已正确 +100）。

修复：新增 `scheduleLookaheadSec = 0.1` 常量，`play()` 与循环分支的 `playbackWallStart`
补 `+ scheduleLookaheadSec * 1000`，四处统一来源。

**但实测问题依旧** —— 100ms 只是小头，真正主因在首次初始化。

## 浏览器实测定位（agent-browser，dev server 5173）

在页面注入脚本包装 `AudioContext`，采样 `performance.now()` ↔ `currentTime` 映射，复现「导入 → 首次播放」：

- **首次播放**：ctx 于 t≈34879 创建（state 已 `running`），但 `currentTime` 直到 **t≈35328 才从 0 开始推进，
  冻结约 450ms**（渲染管线冷启动）。调度发生在 t≈34883，此时 `baseTime = 0 + 0.1 = 0.1`；
  而 UI 指示器 `playbackWallStart = 调度时刻 + 100ms`。音频要等 ctx 时钟走到 0.1（≈t=35415）才发声，
  **偏差 ≈ 430ms**（正好"几个格子"）。
- **后续播放**（ctx 时钟已活）：首个音符发声时刻与指示器第 0 列几乎重合（偏差 < 1ms）。

结论：**AudioContext 首次创建后 `currentTime` 有一段数百 ms 的启动冻结期**，
首次播放用冻结的 `currentTime` 作调度基准，导致预调度的音符整体晚发声；
暂停/停止后 ctx 时钟已正常，故再播放同步。

## 修复方案（第二轮）

调度前等待渲染时钟真正启动，确保 `baseTime` 基准与 wall clock 对齐：

1. `music-engine.ts` 新增 `waitForClockRunning(timeoutMs = 2000)`：轮询直到
   `ctx.currentTime > 0`（时钟已活）或超时，返回是否成功。
2. `sequencer.ts` 的 `play()` 在 `engine.init()` 之后调用 `await engine.waitForClockRunning()`。

首次播放：等待数百 ms 让时钟启动后，`baseTime = currentTime(>0) + 0.1`，与 wall clock 同速对齐；
后续播放时钟已活，立即返回，无额外延迟。

## 验证

- 浏览器实测（agent-browser）：首轮修复后首次播放偏差 **+430ms** → 第二轮修复后 **-9ms**（±50ms 定时器误差内，同步）。
- `vue-tsc -b` 类型检查通过。
- `vite build` 打包通过（沙箱 safe-delete 无法清空旧 `dist/`，改用 `--outDir dist-verify --emptyOutDir false` 验证）。

## 备注

- 修复仅涉及播放时序，不涉及记谱语法 / 声部 / 速度调号等核心契约，`types.ts` 与 `note-map.ts` 无需改动。
- `waitForClockRunning` 的等待只影响「点击到开始播放」的总延迟（首次约数百 ms），不影响音画相对同步；
  超时 2000ms 兜底，时钟永不启动（如无声卡环境）时退回原行为。
- 输入音符的预览音（`NotationGrid.playNote`）也会在首次触发 `engine.init()`，
  但其走「立即播放」路径、不经过 `waitForClockRunning`，不受影响。
- 调试用 DEV 钩子（`window.__board.loadScore`）与诊断脚本已全部移除。
